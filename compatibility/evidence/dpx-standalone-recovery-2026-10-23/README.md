# DPX diagnostic recovery after workspace loss

This directory preserves the observations and code that could be recovered after workspace maintenance removed the working repository, runtime and the new standalone DPX evidence on 2026-10-23. It is a recovery record, not a replacement execution receipt. No new Blender test case or parity credit is recorded here.

## What was actually observed before the loss

The unmodified-library standalone diagnostic completed its native input generation, compile and link with exit 0. Its four separate Node/Wasm processes each returned 3 after the diagnostic caught `std::length_error`, whose message was `vector`, during `read_image`.

The four operations were the native file-writer input read through memory, the same input read through a file, the native memory-writer input read through memory, and that input read through a file. The file reads were diagnostic comparisons; the original Blender Python test loads both byte streams from memory.

Each observed header described a 32 by 32, four-channel, 8-bit DPX image with descriptor 51, no user data and a data offset of 8192. Each decoder opened the image as four-channel UINT8, then received the original 4-byte X stride and negative 128-byte Y stride. The completed capture reported no timeout or capture error and reported its original input closure and generated bytes unchanged.

The original completed receipt was reported as 2,048,978 bytes with SHA-256 `c7d69f18506349baa47888cd687d8d33af514d32b3877e771fa1c91544cabeaa`. Those receipt bytes and the underlying raw logs were not recovered. The recorded digest is an identification of the lost artifact, not proof that this directory contains it. `retained-tool-observations.json` transcribes the relevant tool outputs and labels that provenance explicitly.

## Controlled comparison status

The controlled comparison was actually launched. Before maintenance, its single-object compilation returned 0, and replacement of that object in an isolated copied archive returned 0. A subsequent read of its live receipt observed 103 ordered archive records: 101 objects, one symbol index and one long-name table. The comparison accepted exactly one changed object payload, `DPXColorConverter.cpp.o`, which changed from 9,919 to 9,929 bytes, plus the symbol index. The other 100 object payloads remained equal at that observation.

The link step was still running at the final observed receipt read. Its exit and all four controlled runtime results remain unknown. After maintenance, the tool reported `Unknown process id 29200`; no matching live process or recoverable open file descriptor was observed. There is no observed successful modified-library decode to claim.

The unmodified baseline used a locally built OIIO archive whose bytes differed from the crashing CI archive. Its inputs were newly generated with native Blender, not bytes exported from the crashing browser process. These limitations continue to apply to the retained observations.

## Reconstructed code

`reconstructed-code/run-baseline.py` was transcribed from the complete retained tool output. It is 13,333 bytes and its SHA-256 is `8a6b9316adeae5073ee82f143731c1f5b8004c4fbd7e082bab9a0230c556ab72`, exactly matching the independently recorded pre-maintenance script digest.

`reconstructed-code/run-one-object-comparison.py` was transcribed from the retained authoring call and its later narrow correction. It is 20,007 bytes and its SHA-256 is `d4971368a0d0fd90ac30b86fe6f158e669a25eca6925e86f336da28502edb90e`, exactly matching the pre-maintenance script digest. That correction selected only the first active occurrence of each expression because the original file also contains an inactive later implementation. The script still required the exact reviewed whole-file preimage, patch bytes and postimage.

`reconstructed-code/dpx-probe.cpp` was transcribed from its complete retained source display. Its recovered contents are 8,493 bytes with SHA-256 `61cc9b26272906e002ccb541f421dd68c21a129a378ae4fada58fe162d448a42`. A historical per-file digest was not retained in the available context, so equality to the original file is not independently verified by a pre-maintenance digest. The prior complete input-closure digest alone cannot establish this individual file's equality.

`reconstructed-code/prospective-source-fix.patch` was regenerated from the newly retrieved exact OIIO source preimage and the retained two-expression transformation. Its 716 bytes hash to `09d43b9a0ad95165198e746fa77c012b5f63be94054a60af9b4101002f791233`, matching the previously reviewed patch. Its source preimage and postimage hashes are `793e53edfac8dc79b8cea7bf0cc15c29a23b947e5559cf65cbe4bafd7227ebf1` and `28dd63ce548ee759f09bd23c2a90040408e3f91ffdfc7be3888fb357ad11d9b3` respectively. This is reconstruction after loss, not recovery of the old on-disk patch file.

The two Python scripts were parsed for syntax without running their entry points. They still refer to the original lost closure and runtime paths; they are preserved for review and future deliberate derivation, not presented as a presently complete runnable bundle. The native input generator, preparation script, generated DPX bytes, original raw receipts, static libraries, compiled objects and linked programs were not reconstructed as historical artifacts.
